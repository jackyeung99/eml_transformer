# CLI Reference

The EML Energy Forecasting Pipeline provides a command-line interface for running pipeline stages, multi-stage workflows, and configuration inspection commands.

Commands are executed through `uv`:

```bash
uv run eml_transformer <command> [options]
```

Display the available commands:

```bash
uv run eml_transformer --help
```

Display help for a specific command:

```bash
uv run eml_transformer <command> --help
```

The command help generated by the installed application is the authoritative reference for currently supported options.

## Configuration

Most commands require a configuration file:

```bash
--config configs/dev.yaml
```

Common configurations include:

```text
configs/dev.yaml
configs/prod.yaml
```

The selected file determines:

- Storage backend
- Enabled sources
- Allowed source stages
- Feature definitions
- Dataset definitions
- Model definitions
- Component-specific settings

Local development should normally use:

```bash
--config configs/dev.yaml
```

## Stages and Workflows

A **stage** runs one processing operation.

Examples include:

- Ingesting one source
- Standardizing one source
- Building one feature set
- Training one model

A **workflow** runs several related stages in sequence using the enabled components in the configuration.

Stages are useful for development, debugging, and rerunning one part of the system. Workflows are useful for regular end-to-end execution.

## Command Summary

| Area | Command | Purpose |
|---|---|---|
| Inspection | `inspect` | Lists configured sources, features, datasets, or models. |
| Ingestion | `ingest` | Retrieves recently available source records. |
| Ingestion | `backfill` | Retrieves records over a historical date range. |
| Standardization | `standardize` | Converts Bronze records into standardized Silver records. |
| Text processing | `scrape` | Retrieves or enriches full text for supported sources. |
| Text processing | `embed` | Converts standardized or enriched text into embeddings. |
| Features | `features` | Builds one configured feature set. |
| Datasets | `dataset` | Builds one configured model-ready dataset. |
| Modeling | `train` | Trains and evaluates one configured model. |
| Modeling | `forecast` | Generates forecasts using a trained model. |
| Workflows | `workflows` | Runs a configured multi-stage processing workflow. |

## Inspect Commands

Inspection commands show which components were loaded from the selected configuration.

Use them before running a stage to confirm that a component is enabled and configured correctly.

### List Sources

```bash
uv run eml_transformer inspect sources \
    --config configs/dev.yaml
```

The output may include:

- Source name
- Enabled status
- Source type
- Allowed stages
- Source-specific configuration

Use this command after adding a source to verify that its registration and import path are correct.

### List Features

```bash
uv run eml_transformer inspect features \
    --config configs/dev.yaml
```

The output may include:

- Feature name

### List Datasets

## Incremental Ingestion

Incremental ingestion retrieves the records currently available for a source.

```bash
uv run eml_transformer ingest \
    --source eia_region \
    --config configs/dev.yaml
```

### Required Options

| Option | Description |
|---|---|
| `--source` | Name of the configured and registered source. |
| `--config` | Path to the application configuration file. |

The source must:

- Be enabled
- Include `ingest` in its allowed stages
- Be registered and imported
- Have valid source-specific settings

The ingestion pipeline uses its checkpoint and configured lookback behavior to determine the request period.

A successful run may retrieve zero records if the source has not published anything new.

### Output

Incremental ingestion writes Bronze source records and updates the source checkpoint after a successful run.

```text
External API
    ↓
ingest
    ↓
Bronze records
```

## Historical Backfill

Historical backfill retrieves records over a requested date range.

```bash
uv run eml_transformer backfill \
    --source eia_region \
    --from-date 2026-01-01 \
    --to-date 2026-02-01 \
    --window-days 7 \
    --config configs/dev.yaml
```

### Options

| Option | Description |
|---|---|
| `--source` | Source to backfill. |
| `--from-date` | Beginning of the requested historical period. |
| `--to-date` | End of the requested historical period. |
| `--window-days` | Number of days included in each request window. |
| `--config` | Path to the application configuration file. |

The source must:

- Include `backfill` in its configured stages
- Declare that it supports historical retrieval
- Accept the requested start and end times

The pipeline divides the requested period into smaller windows. Smaller windows reduce the size of individual API requests and make failures easier to retry.

Begin with a short date range before starting a large historical backfill.

## Standardization

Standardization converts Bronze source payloads into shared Silver records.

```bash
uv run eml_transformer standardize \
    --source eia_region \
    --config configs/dev.yaml
```

### Required Options

| Option | Description |
|---|---|
| `--source` | Source whose Bronze records should be standardized. |
| `--config` | Path to the application configuration file. |

The source must include `standardize` in its configured stages.

The pipeline:

1. Reads the source's Bronze records.
2. Calls the source's `standardize_record()` method.
3. Records successful and failed conversions.
4. Writes successful Silver records as Parquet batches.

```text
Bronze records
    ↓
standardize
    ↓
Silver records
```

## Text Scraping

The scraping stage retrieves or enriches full text for a supported source.

```bash
uv run eml_transformer scrape \
    --source gdelt \
    --config configs/dev.yaml
```

### Required Options

| Option | Description |
|---|---|
| `--source` | Text source to process. |
| `--config` | Path to the application configuration file. |

The source must include `scrape` in its allowed stages.

Scraping is appropriate when standardized records contain document metadata or URLs but do not contain the complete text needed downstream.

The scraper may:

- Retrieve article pages
- Extract primary text
- Clean page content
- Preserve scraping metadata
- Record per-document failures

Sources that already provide complete text do not require this stage.

## Embedding Generation

The embedding stage converts standardized or enriched text into numeric vectors.

```bash
uv run eml_transformer embed \
    --source miso_notifications \
    --config configs/dev.yaml
```

### Required Options

| Option | Description |
|---|---|
| `--source` | Text source whose records should be embedded. |
| `--config` | Path to the application configuration file. |

The source must include `embed` in its allowed stages, and the required embedding dependencies must be installed:

```bash
uv sync --extra embeddings
```

The output is written as a Gold embedding dataset.

```text
Silver or enriched text
    ↓
embed
    ↓
Gold embeddings
```

## Feature Building

The feature stage runs one configured feature builder.

```bash
uv run eml_transformer features \
    --name eia_region_hourly \
    --config configs/dev.yaml
```

### Required Options

| Option | Description |
|---|---|
| `--name` | Name of the configured feature definition. |
| `--config` | Path to the application configuration file. |

The feature definition specifies:

- Registered builder
- Single input dataset
- Gold output dataset
- Builder settings

The pipeline:

1. Loads the feature definition.
2. Resolves the registered builder.
3. Reads the configured input.
4. Passes the input DataFrame and settings to the builder.
5. Writes the returned Gold feature set.

```text
Silver or derived input
    ↓
features
    ↓
Gold feature set
```

## Dataset Building

The dataset stage combines configured feature sets into one model-ready dataset.

```bash
uv run eml_transformer dataset \
    --name load_forecasting \
    --config configs/dev.yaml
```

### Required Options

| Option | Description |
|---|---|
| `--name` | Name of the configured dataset definition. |
| `--config` | Path to the application configuration file. |

The dataset definition specifies:

- Registered dataset builder
- Input feature mappings
- Gold output dataset
- Builder settings

The configured input names become the keys passed to the builder:

```python
inputs["region_features"]
inputs["interchange_features"]
```

```text
Gold feature sets
    ↓
dataset
    ↓
Gold model-ready dataset
```

## Model Training

The training stage fits and evaluates one configured forecasting model.

```bash
uv run eml_transformer train \
    --model miso_hourly_load_ridge \
    --config configs/dev.yaml
```

### Required Options

| Option | Description |
|---|---|
| `--model` | Name of the configured model definition. |
| `--config` | Path to the application configuration file. |

The model definition specifies:

- Model implementation
- Training dataset
- Target column
- Feature columns
- Hyperparameters
- Training window
- Validation window
- Retraining interval
- Model artifact output

The training pipeline:

1. Loads the training dataset.
2. Selects the configured time window.
3. Splits training and validation data.
4. Resolves and fits the model.
5. Calculates evaluation metrics.
6. Writes the model and its metadata.

### Force Retraining

If supported by the command, use `--force` to train even when the stored model is still within its configured retraining interval:

```bash
uv run eml_transformer train \
    --model miso_hourly_load_ridge \
    --force \
    --config configs/dev.yaml
```

Without `--force`, training may be skipped when the current model does not yet require retraining.

## Forecast Generation

The forecasting stage loads a trained model and generates future predictions.

```bash
uv run eml_transformer forecast \
    --model miso_hourly_load_ridge \
    --config configs/dev.yaml
```

### Required Options

| Option | Description |
|---|---|
| `--model` | Name of the configured model definition. |
| `--config` | Path to the application configuration file. |

The forecasting pipeline:

1. Loads the trained model and metadata.
2. Reads the configured forecast input.
3. Constructs the required model features.
4. Generates predictions.
5. Writes the forecasts to the configured Gold dataset.

```text
Model artifact + forecast input
    ↓
forecast
    ↓
Gold forecast records
```

The model must be trained before forecasting unless the workflow trains it automatically.

## Workflows

Workflows run several processing stages in sequence.

### Numeric Workflow

```bash
uv run eml_transformer workflows numeric \
    --config configs/dev.yaml
```

A numeric workflow may include:

```text
Ingestion
    ↓
Standardization
    ↓
Feature building
    ↓
Dataset building
    ↓
Training
    ↓
Forecasting
```

Only enabled components and applicable stages from the selected configuration are included.

### Text Workflow

When supported, run the text workflow:

```bash
uv run eml_transformer workflows text \
    --config configs/dev.yaml
```

A text workflow may include:

```text
Ingestion
    ↓
Standardization
    ↓
Optional scraping
    ↓
Embedding
```

The exact stages depend on each source's configured stage list.

## Structured Results

Pipeline stages return structured result objects to the CLI.

Results may include:

- Status
- Component name
- Input and output paths
- Records read
- Records written
- Failed records
- Elapsed time
- Skip reason
- Error information

The pipeline communicates what happened, while the CLI formats that information for display.

A command may report a status such as:

| Status | Meaning |
|---|---|
| `completed` | The operation completed successfully. |
| `skipped` | The operation was intentionally not required. |
| `empty` | The operation completed but found no records to process. |
| `failed` | The operation could not complete successfully. |

The exact statuses depend on the pipeline result type.

## Exit Behavior

A successful command should exit with status code `0`.

A failed command should return a nonzero status so ECS, scheduling, and automation systems can identify the failure.

A successful run that retrieves no new records is generally not considered a failure.

## Common Usage Pattern

Use this sequence when testing a new numeric source:

```bash
uv run eml_transformer inspect sources \
    --config configs/dev.yaml
```

```bash
uv run eml_transformer ingest \
```


```bash
uv run eml_transformer features \
```

```bash
uv run eml_transformer dataset \
    --name new_dataset \
    --config configs/dev.yaml
```

## Troubleshooting

### Component is not found

Check that:

- The component is configured.
- It is enabled.
- Its registered name matches the configuration.
- Its module is imported.
- The correct configuration file was selected.

### Stage is not allowed

Confirm that the stage is listed for the source:

```yaml
stages:
  - ingest
  - backfill
  - standardize
```

### No records were retrieved

Check:

- Source publication timing
- Checkpoint state
- Lookback settings
- Requested date range
- API availability
- Source filters

A source may not have published new records before the scheduled run.

### Dataset input does not exist

Run the upstream stage first.

For example:

```text
features require Silver records
datasets require feature sets
training requires a model-ready dataset
forecasting requires a trained model
```

### API key is missing

Confirm that the expected environment variable is available:

```bash
printenv EIA_API_KEY
```

Do not include the secret value in shared logs or documentation.

### Command syntax has changed

Display the installed command help:

```bash
uv run eml_transformer --help
```

```bash
uv run eml_transformer <command> --help
```
